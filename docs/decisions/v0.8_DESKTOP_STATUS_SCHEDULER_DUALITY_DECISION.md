# v0.8 Desktop Status Scheduler Duality Decision

## Status

✅ **Accepted** — implemented 2026-06-17 during Stage 5+1 WIP landing

## Context

After Stage 5 landed the 7-state product surface (commit `9cdfa2b`), a follow-up WIP introduced a new file `src/runtime/schedulerService.ts` (279 lines, 2026-06-16) implementing `createSchedulerService()`. This created a dual-scheduler situation in the codebase:

| File | API | Caller | Semantics |
|------|-----|--------|-----------|
| `src/state/desktopStatusScheduler.ts` (271 lines) | `scheduleDesktopStatus(input) → decision` | `src/state/desktopStatusState.ts` (resolver, called per render) | Pure function, snapshot in/out |
| `src/runtime/schedulerService.ts` (279 lines) | `createSchedulerService() → { start, stop, updateKinds, setPreferred, clearPreferred, subscribe, getSnapshot }` | `src/features/desktop/hooks/useDesktopStatusRuntime.ts` (React hook, called per render + useEffect) | Stateful service, 250ms `setInterval` ticker |

The two files share ~90% of their decision logic (priority lookup, media/resident alternation window, preferred-kind pinning, stability window, preemption window), differ only in lifecycle packaging.

The Stage 5 WIP commit (`9cdfa2b`) and the WIP plan (`docs/plans/STAGE5_WIP_LANDING.md`) do not mention `schedulerService.ts`. It was added between plan authorship and the WIP landing, without a recorded rationale.

The current state creates several risks:

1. **Drift risk**: the two implementations will diverge over time. `useDesktopStatusRuntime.vitest.ts:57` already warns "20_000 ms per desktopStatusScheduler — keep this in sync if it changes".
2. **Onboarding cost**: new contributors must understand why two files do the same thing.
3. **Test coverage gap**: `runtime/schedulerService.ts` has zero tests, while `state/desktopStatusScheduler.ts` has 295 lines of tests.
4. **Decision trail**: the absence of a recorded rationale means future maintainers will repeatedly re-litigate the choice.

## Decision

**Adopt Option A: keep the dual implementation, document the boundary, and codify it with comments + test coverage.**

The pure function in `state/desktopStatusScheduler.ts` remains the **resolver snapshot path** (called per render with the latest input snapshot). The stateful service in `runtime/schedulerService.ts` becomes the **hook event path** (started in `useEffect`, holds state across renders, drives the wall-clock alternation heartbeat).

### Boundary Rules (codified in source)

1. **Resolver path** (`state/desktopStatusScheduler.ts`):
   - Synchronous, deterministic, pure
   - Returns one `ScheduleDecision` per call
   - Caller (`desktopStatusState.ts`) is invoked inside React render
   - Time source: `input.now` (testable, no `Date.now()` inside)
   - No side effects, no subscriptions

2. **Hook path** (`runtime/schedulerService.ts`):
   - Stateful, lifecycle-managed, single instance per `useDesktopStatusRuntime` call
   - Internally calls a 250ms `setInterval` to drive alternation
   - Notifies subscribers via `subscribe(listener)` when the decision changes
   - Time source: `Date.now()` (production); injectable for tests
   - Side effects: timer, listener fan-out

### Why Not Option B (collapse to a single layer)

Option B would inline the pure function into the service. This breaks React's render purity: every render would re-execute the service's tick logic, causing double-execution. The dual-layer design exists precisely because the resolver runs in render (sync, no side effects) and the hook runs in effect (async, with side effects).

### Why Not Option C (collapse to a single pure function)

Option C would delete the service and have the hook call `scheduleDesktopStatus` inside `useSyncExternalStore`. This works in principle, but loses the wall-clock heartbeat that drives the 15s media/resident alternation. The heartbeat is the entire reason `useDesktopStatusRuntime.ts` needs a long-lived state holder — without it, alternation stalls until the next provider event arrives (which can be minutes while music plays).

## Consequences

### Positive

- **Two call sites, two abstractions**: each matches its calling context (pure function for render, stateful service for effect).
- **Testability preserved**: `state/desktopStatusScheduler.ts` keeps 295 lines of fast pure tests; `runtime/schedulerService.ts` gets its own vitest with timer mocking.
- **No regression risk**: the dual implementation is already in `git status`; we are accepting it, not introducing it.

### Negative

- **Documentation burden**: the boundary must be explained in `ARCHITECTURE.md` and inline in both files.
- **Future maintenance cost**: if a third consumer appears (e.g., a Tauri command that wants to ask the scheduler "what would you show right now?"), it should use the pure function path. This must be re-decided each time.
- **Code duplication**: ~270 lines of decision logic in two places. Mitigated by keeping both implementations under 300 lines each and documenting the diff in a comment header on both.

### Neutral

- **No API change for callers**: `useDesktopStatusRuntime.ts` keeps its current call shape. `desktopStatusState.ts` keeps its current call shape.

## Safe Follow-Up Slices

If Option A proves unworkable in practice, the next reversible slice is:

1. **Extract a shared `computeDesktopStatusDecision(input)`** into `state/desktopStatusScheduler.ts` and have `runtime/schedulerService.ts` import and wrap it. The service adds only the timer + listener fan-out; the decision logic lives in one place. This keeps Option A's semantics while removing the duplication.

This follow-up is **explicitly out of scope** for Stage 5+1. The current decision accepts the duplication.

## Stop Conditions

This decision should be re-litigated if:

- The duplication grows beyond 400 lines per file.
- A third consumer appears that needs scheduler output (would force extraction).
- The alternation heartbeat is removed (would let Option C work).
- A future React 19+ feature makes `useSyncExternalStore` the canonical pattern (would let Option C work natively).

## Current Boundary

After this decision is accepted:

- `state/desktopStatusScheduler.ts` = resolver snapshot path (pure)
- `runtime/schedulerService.ts` = hook event path (stateful)
- Both files exist on `main` after Stage 5+1 lands
- `ARCHITECTURE.md` documents the boundary
- `useDesktopStatusRuntime.ts` uses the service; `desktopStatusState.ts` uses the pure function
- No code outside these four files may import `schedulerService` or `scheduleDesktopStatus` directly
