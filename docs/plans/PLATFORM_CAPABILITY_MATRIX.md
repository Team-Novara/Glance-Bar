## How to read this matrix

- **These are capability states, not claims.** A row says what the code
  implements and what evidence exists — it never says "this works on that
  platform". "Compile-time support is not feature parity; no macOS/Linux
  capability claims are made" ([KNOWN_LIMITATIONS.md](../release/KNOWN_LIMITATIONS.md) §4).
- **State vocabulary** (capability states used in the table):
  - **real (Windows-verified)** — implemented, with recorded Windows
    verification evidence; the Windows MVP evidence gaps that remain are
    named in the evidence column.
  - **real — automated coverage only** — implemented in code with automated
    test coverage, but not yet demonstrated on physical Windows hardware, a
    packaged build, or real testers ([KNOWN_LIMITATIONS.md](../release/KNOWN_LIMITATIONS.md)
    "pending evidence" definition).
  - **real (shared code path) — unverified on platform** — the capability
    ships as platform-agnostic code with no platform gate; it compiles for
    the target (CI runs Rust checks on all three OSes, KNOWN_LIMITATIONS
    §1.2/§4) but has no recorded runtime evidence on that platform.
  - **gated behind `*_VALIDATED = false`** — a complete implementation
    exists, but a module-level gate const keeps the capability reporting its
    bounded `unsupported`/stub payload exactly as before. Per the STAGE6
    rule "validate on real target hardware before changing a capability
    from unsupported to available" (STAGE6_CROSS_PLATFORM_DESIGN.md:18),
    the gate flips only together with recorded real-hardware evidence and
    the updated gate test.
  - **stub — unavailable by design** — an explicit bounded
    `unsupported`/no-op stub; no implementation, no gate. Includes the
    "honest not-implemented" family (`system.rs:222-246`) and the developer
    states with no native contract.
  - **unsupported with research** — the stub is the honest terminal state
    per a recorded feasibility verdict; reopen conditions are documented.
- **Scope notes.** `get_notification_summary` is derived from the focus read
  on every platform (`commands/focus.rs:101-123`), so it lives inside the
  focus rows. `get_app_runtime_metadata` (bounded app version / platform /
  runtime facts, `commands/diagnostics.rs:16-22`) has no platform dimension
  and no capability claim, so it is not a row. `pause/resume/cancel_download`
  belong to the downloads rows.
- **Evidence discipline.** Every citation is a tree fact: `file:line` for
  code, a docs section for recorded evidence, and a PR number from
  [GLANCE_BAR_PLAN.md](GLANCE_BAR_PLAN.md) or the git log. Where the tree
  records no PR for a piece of baseline code, that is stated rather than
  invented. Gates verified during this compilation: `cargo test
  --manifest-path src-tauri/Cargo.toml` — 97 passed / 0 failed on this
  worktree (WSL Ubuntu, Linux target), and the four gate-off contract tests
  re-run by name filter (`cargo test --manifest-path src-tauri/Cargo.toml
  gate`): `media::linux`, `media::macos`, `commands::focus::linux`, and
  `window::linux` all ok — 4 passed / 0 failed, 93 filtered.

## Maintenance rule

Update this matrix **in the same PR that changes a gate const, names a new
gate, or lands validation evidence** — mirroring the maintenance rules of
[STAGE6_CROSS_PLATFORM_DESIGN.md](STAGE6_CROSS_PLATFORM_DESIGN.md) (flip a
gate only together with recorded real-hardware evidence and the updated gate
test) and [KNOWN_LIMITATIONS.md](../release/KNOWN_LIMITATIONS.md) (update in
the same change that records new evidence). When a gate flips: change the
state to the verified form, move the evidence citation into the "Validation
evidence so far" column with the PR number, and empty the "What flips it
live" cell into the next concrete open step. When a capability is added,
renamed, or removed in code, add or retire its rows in the same change and
re-check the gate const index. Never mark a row with evidence this
repository does not record; if a fact is not in the tree, write `unknown`
rather than a plausible guess.
